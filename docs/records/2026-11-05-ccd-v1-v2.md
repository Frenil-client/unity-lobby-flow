# CCD 패치 기록 — v1 → v2 (Windows)

LocalServer로 검증한 패치 과정(`2026-11-04-content-update-v2.md`)을 Unity CCD로 다시 확인한 기록. 절차는 SPEC 5.7, CCD 구성은 SPEC 5.4·5.5를 따랐다.

## 조건

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-05 |
| CCD | 프로젝트 `9211a594-db04-43bd-bd55-c6d120db13de`, 환경 production, 공개 버킷 `lobby-flow-windows`(`524e51c0…`), 배지 `latest` |
| 업로드 | 메뉴 **CCD ▸ 현재 플랫폼 업로드와 릴리스** → `ugs ccd entries sync … -r`(UGS CLI 2.0, 서비스 계정) |
| 플레이어 | Windows 개발 빌드. CCD 프로필로 v1 전체 빌드 직후 만들었다 |
| 기준 | `main` `3bd5da3`의 v1 콘텐츠, v2는 `content/v2` `b749cde`의 `Remote/` |
| 로컬 콘텐츠 서버 | 켜지 않음. 업로드 뒤 서버 요청 0건 |

## CCD 상태

| 단계 | 릴리스 | `latest` 배지 | 카탈로그 해시 |
|---|---|---|---|
| v1 전체 빌드 업로드 | 1 | 릴리스 1 | `54f4d144…` |
| v2 업데이트 빌드 업로드 | 2 | 릴리스 2로 자동 이동 | `0200432b…` |

- 배지를 따로 지정하지 않아도 CCD가 새 릴리스에 `latest`를 옮겼다.
- 공개 주소(`…/release_by_badge/latest/entry_by_path/content/?path=/파일`)에서 카탈로그 해시와 번들을 인증 없이 받았다(curl, 200). 받은 해시는 로컬 빌드 결과와 같았다.
- 업로드는 지우기 옵션 없이 해서 릴리스 2에도 v1 번들이 남는다. 이전 카탈로그를 가진 플레이어가 계속 받을 수 있다.

## 플레이어 결과 (`Player.log`)

| 실행 | 결과 |
|---|---|
| v1, 캐시 삭제 후 재부팅 | `갱신 False, 받을 크기 0.1MB` → 다운로드 → 로비. 챕터 2 진입 시 추가 다운로드 |
| v2 업로드 뒤, 캐시 유지 | `카탈로그 변경 1개, 갱신한다` → `갱신 True, 받을 크기 0.1MB` → 다운로드. 코스튬 3 → 4. 챕터 2 진입 시 다시 받음 |

화면(봄 배너와 공지, 봄 축제 코스튬, 챕터 2 수정 9개)은 사용자가 확인했다. CCD 쪽에는 요청 로그가 없어 번들별로 받은 바이트는 기록하지 않았다. 바뀐 번들과 크기는 LocalServer 기록의 후속 2절과 같다(같은 콘텐츠, 같은 해시).

## 배지 전환 (Windows, 개발 빌드)

CCD 릴리스에 `v1`(릴리스 1), `v2`(릴리스 2) 배지를 붙이고, 개발 빌드의 테스트 메뉴 **CCD 콘텐츠**로 받을 배지를 바꿨다. 플레이어는 Boot·로비 씬만 다시 만든 뒤 빌드했다(Addressables 빌드는 그대로).

| 실행 | 배지 | 결과(`Player.log`) |
|---|---|---|
| 1 | v1(기본) | 이전에 받아 둔 v2 카탈로그에서 `카탈로그 변경 1개, 갱신한다` → `갱신 True` → 코스튬 3(v1로 내려감). 캐시 삭제 뒤 Boot에서 0.1MB 받기, 챕터 2 받기. 테스트 메뉴에서 `CCD 콘텐츠 v2 선택(현재 실행은 v1)` |
| 2 | v2(앱 재시작) | `카탈로그 변경 1개, 갱신한다` → `갱신 True, 받을 크기 0.1MB` → 코스튬 4. 챕터 2 다시 받기 |

- 배지를 바꾸면 v1 → v2뿐 아니라 v2 → v1로도 카탈로그가 바뀐다. Addressables는 원격 카탈로그 해시가 캐시된 것과 다르면 방향과 상관없이 갱신한다.
- 화면 확인(겨울 → 봄)은 사용자가 했다.

## 기준 다시 만들기: 공통 번들 이름 고정

Jenkins 작업 폴더(`lobby-flow`)에서 만든 번들 이름이 로컬(`unity-lobby-flow`)과 달랐다. Addressables 기본값이 공통 번들(`unitybuiltinassets`, `monoscripts`) 이름을 프로젝트 폴더 이름의 해시로 짓고, 이 번들에 의존하는 씬·폰트 번들 해시까지 바뀌기 때문이다. 접두어를 `lobbyflow`로 고정한 뒤 두 플랫폼의 기준과 CCD 릴리스를 다시 만들었다(이전 기준으로 만든 플레이어는 새 릴리스와 맞지 않는다).

| 버킷 | v1 | v2 (= latest) |
|---|---|---|
| `lobby-flow-windows` | 릴리스 3, `1e8dd85b…` | 릴리스 4, `3db58da8…` |
| `lobby-flow-android` | `ce3bdde4…` | `80e1d0eb…` |

- 공통 번들은 `lobbyflow_monoscripts_1aba66b1…`(두 플랫폼 같음), `lobbyflow_unitybuiltinassets_…`(플랫폼마다 다름).
- 업로드 직후 CCD 안의 배지는 바로 옮겨지지만, 공개 주소는 1~2분 동안 이전 릴리스를 돌려줬다(Windows v2). Jenkins 원격 검증 대기 시간을 최대 4분으로 늘렸다.

## 기준 다시 만들기: 챕터 그룹 분리, Jenkins `content-release` (2026-11-06)

Jenkins 빌드 #7(Android 전체 빌드)과 로컬 번들을 비교해 번들 이름 고정을 확인하던 중, v2 카탈로그에서 챕터 1 재질(Floor, Prop)이 `local_chapter01_assets` 대신 씬 번들 `local_chapter01_scenes`를 가리키고 assets 번들 위치가 빠진 것을 발견했다(Windows, Android 둘 다). 원인과 구성 규칙은 SPEC 5.2. 챕터 그룹을 씬 파일 항목과 `Materials` 폴더 항목으로 나누고, Jenkins 빌드 #8(`MODE=content-release`, `RELEASE_PLATFORMS=both`, 22분)으로 두 플랫폼의 v1 전체 빌드, 플레이어, CCD v1, v2 업데이트, CCD v2를 한 번에 다시 만들었다. 새 기준 파일은 이 실행의 산출물이다.

| 버킷 | v1 | v2 (= latest) |
|---|---|---|
| `lobby-flow-windows` | 릴리스 5, `b6c03810…` | `d2938a1a…` |
| `lobby-flow-android` | 릴리스 5, `ce3bdde4…` | `7241e554…` |

- 업로드마다 Jenkins가 공개 주소의 `latest`와 배지 해시를 확인했다. v2는 공개 주소에 반영되기까지 약 100~120초 걸렸다(10초 간격 확인 10~12회). 실행 뒤 공개 주소로 다시 받은 6개 해시도 표와 같다.
- v2 카탈로그에서 챕터 1 재질은 두 플랫폼 모두 `local_chapter01_assets`를 가리킨다. 챕터 2(바뀜)와 챕터 3(그대로)의 재질도 각자의 assets 번들을 가리킨다.
- Android v1 카탈로그 해시는 분리 전과 같았다. Windows v1은 달라졌는데, 로컬 폰트 번들(`local_fonts_assets_all_8aa323fe…`)과 Jenkins 폰트 번들(`…_3ebbea25…`)이 19바이트 다르다. 디스크의 폰트 에셋은 둘이 같다. 로컬에서 다시 전체 빌드해도 `8aa323fe…`가 나왔다. 두 번들을 풀어 보니 TMP 모바일 SDF 셰이더의 DX11 블록에서 디버그 청크(SPDB)만 달랐고, 원인은 셰이더의 `enable_d3d11_debug_symbols`였다(SPEC 5.2). 셰이더를 고쳤으므로 기준과 CCD 릴리스를 한 번 더 만든다.
- 이 실행의 APK와 Windows 실행 파일(zip)이 새 릴리스와 맞는 v1 설치본이다. 이전 플레이어는 새 릴리스와 맞지 않는다.

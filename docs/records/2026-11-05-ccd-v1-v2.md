# CCD 패치 기록 — v1 → v2 (Windows)

LocalServer로 검증한 패치 과정(`2026-11-04-content-update-v2.md`)을 Unity CCD로 다시 확인한 기록. 절차는 SPEC 5.7, CCD 구성은 SPEC 5.4·5.5를 따랐다.

## 조건

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-05 |
| CCD | 프로젝트 `9211a594-db04-43bd-bd55-c6d120db13de`, 환경 production, 공개 버킷 `lobby-flow-windows`(`524e51c0…`), 배지 `latest` |
| 업로드 | 메뉴 **CCD ▸ 현재 플랫폼 업로드와 릴리스** → `ugs ccd entries sync … -r`(UGS CLI 2.0, 서비스 계정) |
| 플레이어 | Windows 개발 빌드. CCD 프로필로 v1 전체 빌드 직후 만들었다 |
| 기준 | `main` `3bd5da3`의 v1 콘텐츠, v2는 `content/v2` `b749cde`의 `Remote/` |
| 로컬 콘텐츠 서버 | 켜지 않음. 업로드 뒤 서버 요청 0건 |

## CCD 상태

| 단계 | 릴리스 | `latest` 배지 | 카탈로그 해시 |
|---|---|---|---|
| v1 전체 빌드 업로드 | 1 | 릴리스 1 | `54f4d144…` |
| v2 업데이트 빌드 업로드 | 2 | 릴리스 2로 자동 이동 | `0200432b…` |

- 배지를 따로 지정하지 않아도 CCD가 새 릴리스에 `latest`를 옮겼다.
- 공개 주소(`…/release_by_badge/latest/entry_by_path/content/?path=/파일`)에서 카탈로그 해시와 번들을 인증 없이 받았다(curl, 200). 받은 해시는 로컬 빌드 결과와 같았다.
- 업로드는 지우기 옵션 없이 해서 릴리스 2에도 v1 번들이 남는다. 이전 카탈로그를 가진 플레이어가 계속 받을 수 있다.

## 플레이어 결과 (`Player.log`)

| 실행 | 결과 |
|---|---|
| v1, 캐시 삭제 후 재부팅 | `갱신 False, 받을 크기 0.1MB` → 다운로드 → 로비. 챕터 2 진입 시 추가 다운로드 |
| v2 업로드 뒤, 캐시 유지 | `카탈로그 변경 1개, 갱신한다` → `갱신 True, 받을 크기 0.1MB` → 다운로드. 코스튬 3 → 4. 챕터 2 진입 시 다시 받음 |

화면(봄 배너와 공지, 봄 축제 코스튬, 챕터 2 수정 9개)은 사용자가 확인했다. CCD 쪽에는 요청 로그가 없어 번들별로 받은 바이트는 기록하지 않았다. 바뀐 번들과 크기는 LocalServer 기록의 후속 2절과 같다(같은 콘텐츠, 같은 해시).
